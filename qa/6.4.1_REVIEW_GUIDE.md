# EMS SaaS Industrial 6.4.1 — Independent Review Guide

Base baseline: `cb15919032596021e732321a4c7c84e60429f5f6` (`main`).

This candidate keeps the protected GPIO/storage/resource subsystems from the baseline and applies targeted hardening to command lifecycle, reboot recovery, usage/reset persistence, Pi authentication, device retirement, explicit storage provisioning, and service permissions.

## Critical invariants
- Exactly four physical slots: A/B/C/D.
- Cloud command lifecycle is strict: QUEUED → DELIVERED → EXECUTING → HARDWARE_VERIFIED → COMPLETED → ACKED, with FAILED/EXPIRED branches and UNKNOWN_AFTER_REBOOT recovery.
- A queued command is not directly executable by the Pi.
- Delivery lease is 120 seconds; absolute command expiry is 300 seconds.
- `UNKNOWN_AFTER_REBOOT` is excluded from normal queue claim and requires hardware reconciliation.
- HARDWARE_VERIFIED requires `VERIFIED_ON`, `VERIFIED_OFF`, or `GPIO_CONFIRMED`.
- Visibility requires target_days > 0, physical_toggle exactly ON, and not disabled.
- Feedback-enabled is constrained by actual device feedback capability.
- Retired devices/societies are quarantined; destructive device/society deletion is not used.
- Legacy STATE_VERSION=4 state and legacy SQLite queue schemas migrate/load safely.
- Pi API credentials are sent in headers, not JSON.
- EMS storage must be explicitly supplied as an existing ext4 filesystem; setup never formats it.
- Controller service runs as `pi:pi` with GPIO/I2C supplementary groups.

## Mandatory certification still outside this ZIP
1. Hardware-in-loop contactor tests, feedback polarity/wiring, break-before-make, power loss during interlock, and emergency-stop behavior.
2. 7–30 day storage endurance soak on the exact production USB/storage device; measure logical writes, filesystem/block writes, write amplification, temperature, and errors.
3. Replace startup/ad-hoc DB schema changes with qualified Alembic migrations and test upgrades from real production snapshots.
4. Signed OTA with Ed25519 verification, staged A/B update and rollback.
5. Production frontend authentication using HttpOnly/Secure/SameSite cookies and full CI build/security testing.
6. Dependency vulnerability scan and target Raspberry Pi systemd/device-access validation.
