# EMS SaaS 6.5.0 Hardened Candidate

## Scope
This candidate is based on the 6.4 targeted-hardened package and adds the next industrial hardening gates that can be verified in software.

### P0 deployment blocker resolved
- Removed all PostgreSQL schema DDL from `backend/main.py` startup.
- Added Alembic with a consolidated current-schema migration that also normalizes the legacy wing/slot schema.
- Render now runs `alembic upgrade head` before starting FastAPI.
- The invalid parameterized PostgreSQL DDL for `reset_day` is therefore gone from application startup.

### P0 command lifecycle
- Strict FSM is enforced: `queued -> delivered -> executing -> hardware_verified -> completed -> acked`.
- `queued -> executing` is rejected.
- Delivered commands have a 120-second lease and a 300-second absolute expiry.
- `UNKNOWN_AFTER_REBOOT` is not eligible for normal queue selection.

### P1 web authentication
- Access JWT moved from `localStorage` to an HttpOnly Secure cookie.
- Access token lifetime is 15 minutes.
- Refresh tokens are persisted server-side, expire after 7 days, and rotate on every refresh.
- CSRF double-submit protection is applied to authenticated unsafe requests.
- Frontend uses `withCredentials` and refreshes expired access sessions automatically.
- Legacy bearer-token acceptance remains in the backend only for compatibility/testing; production frontend no longer stores bearer tokens in browser storage.

### Device lifecycle / feedback consistency
- Retired Pi devices cannot be reassigned through society configuration.
- Society/device dashboards expose feedback as enabled only when the physical feedback capability is installed.
- Firmware download requires both device ID and matching API key.

## Explicitly NOT certified yet
1. Physical HIL qualification: contactor weld, feedback loss, and power interruption during the 500 ms interlock.
2. 7-30 day storage endurance soak on the exact production USB media/OS, including measured system WAF.
3. Ed25519-signed firmware + A/B boot + automatic rollback. Firmware transport authentication is tightened, but cryptographic OTA integrity is not claimed complete.
4. Production database migration must be executed against a staging copy and then production with backup/restore verification before release.
5. Frontend production build and Render deployment must be executed in CI/target environments; local static checks are not a substitute.
